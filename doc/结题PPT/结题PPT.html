为什么做它 —— 大学生课程场景的空白

★ 最难难点 ① / 3结构感知父子切片 · 为什么最难 + 父块

检索要「小而精」、问答要「全而准」—— 这对矛盾怎么破

!为什么这是全场最难的一步

  • 切片质量直接决定检索召回的上限——切错，后面再强也白搭（地基）
  • 要同时满足相互冲突的目标：小块利检索精度、大块利问答完整
  • 组合复杂：结构感知（依赖 IR 树）× 多模态分类 × 中文句界 × 原子性保护
  • 业界无标准答案，参数与边界全靠自己实测调

▣父块 Parent · 给问答补全上下文

  • 按 parent_level=N 在 section 树聚合（默认 L1，文档级可调粒度）
  • 分界线上的标题块归入紧随其后的父块，不单独成块
  • 连续空标题（无正文）累积前置到下一父块，防上级标题信息丢失
  • 纯标题容器不出父块；text_full 落库供 Small-to-Big 回填
真机实测：同一份 34 页设计文档，粒度可调 —— L1 = 25 父块 · L2 = 61 · L3 = 111；用户嫌父块太长可在解析透视里手动细分。

★ 最难难点 ② / 3结构感知父子切片 · 子块 + 标题前置

子块 Child —— 把向量检索的精度榨到极限

⛏子块切分（做检索的小粒度块）

  • 句界滑动窗口：max 250 / min 150 token，15% overlap，按 。！？\n 切——拒绝定长硬切（避免切断句意、向量失真）
  • 原子块整体保留：list / code / image / table / 公式不拆，保语义完整
  • title 块不单列子块（已在 header_path 前缀里）
  • 长句兜底硬切——曾因「单句长度落在 (max−overlap, max]」反复重试陷死循环、冻结事件循环，改逐句消费 + 长句硬切 + 回归用例（见 P16）

★ 最难难点 ③ / 3多模态四类双轨 + 设计权衡

一块内容，两种身份 —— 检索用富化文本，问答用原始资产

类型检索用（向量化）问答用（喂大模型）
图片VLM 图像描述 + 转写图中文字原图 base64（多模态路）
表格VLM 摘要（利检索）MinerU 原始 HTML（信息更全）
代码功能说明 + 核心函数/类原始完整代码
公式自然语言含义解释原始 LaTeX
这些结构化富化文本是原子块，切子块时不可拆，必须整体保留完整性。检索基底弃用 MinerU 的纯 OCR（仅识字、不理解图意）。

⚖设计权衡（体现判断）

  • 语义切片（逐句 embedding）上限高但算力贵 → 选「句累加 + 标题前置」够用且省钱
  • 推测问题索引最耗 API → 默认关闭，按需开启
  • 跨页表格「空幽灵块」污染检索 → normalizer 源头丢弃 + 兜底，10→0 垃圾子块
用户搜「标准差公式」不会手写 LaTeX，搜类名不想读注释 —— 所以检索用「人话」、问答给「原件」。
enrichers/enricher.py（并发 3 · qwen-plus）
次难点 · AMinerU 解析 → 自研 IR 标准化与文档树重建（详写 · 略讲）

把「扁平、会漂移」的解析，重建成结构化文档

!真实的坑（不是想象的）

  • 输出扁平：标题层级永远 = 1，拿不到章节树
  • 格式会漂移：字段增删、同名字段语义变（实测出现 reference_list / simple_table·complex_table / Office title.level=2）
  • Office 文档无坐标、无 origin.pdf
  • 官网文档更新滞后且有误 → 以实际调用实测为准

✓自研解法

  • 双层「宽进严出」IR：Raw 层 extra=allow 容错，IR 层严格 Pydantic 校验，脏数据绝不入库
  • LLM 文档树重建：理解标题语义、重建多级 DOM、注入 header_path 面包屑
  • 坐标锚点：保留 bbox 供高亮溯源；Office 自动 OCR 转 PDF 拿坐标
  • 格式漂移监控：每次解析跑 19 项语义校验 + 探针日志（附录 E）
「官网文档不可信、靠实测反推格式 + 持续监控」是本项目最能体现工程较真的地方 —— 详见附录 B / E、《在线 API 输出文件格式（SaaS 推断版）》。

07 / Evaluation检索质量评测 · 可复现脚本

把「效果不弱于大厂」做成可复现的数字

⌗评测方法（消融 + 指标）

  • Gold set：12 条人工标注查询（程序设计基础实训课程 · 19 篇已索引文档 · 含图片类）
  • 指标：Hit@k 命中率 · Recall@k · MRR · nDCG@k（按相关性判定单元去重）
  • 消融配置：BM25(无 jieba) / BM25(jieba) / 向量 / 混合 RRF / 混合 + 重排
  • 脚本：tools/benchmark_retrieval.py —— jieba 消融离线可跑（仅 SQLite，无需 Key）；完整指标需 Key + 已索引数据
实测结果（真机跑出，非估值）
配置Hit@1Hit@3Recall@5MRR
BM25 · 无 jieba0.000.000.000.00
BM25 · jieba0.670.920.730.79
向量0.831.000.800.90
混合 RRF0.751.000.800.86
混合 + 重排0.750.920.800.84
最稳硬结论：jieba 让中文 BM25 Hit@5=0→1.00；完整管线 Top-3 命中率 100%。
诚实说明：本集小而干净，向量检索已近上限，混合 / 重排未再超过它——其价值在更大、更嘈杂语料上才明显，故不为「重排更好」而调数。一条命令可复现。

Appendix G关键问题与解决（STAR 详述）·「证明是我做的」

开发中遇到的四个关键坑，以及我是怎么解决的

① MinerU 扁平树：标题层级恒为 1
问题：解析后所有标题 title_level 都是 1，拿不到真实章节结构，父块没法按标题切。
定位/解决：实测发现官网声称有 title.level 但当前版本恒输出 1 → 改用 LLM 理解标题语义重建多级 DOM 树 + 注入 header_path 面包屑。
结果：文档树可用，父子切片有了结构地基，解析透视能展示真实树。
② 中文 BM25 零召回
问题：中文关键词几乎搜不到，混合检索里关键词一路形同虚设。
定位/解决：排查出 FTS5 unicode61 把整段中文当一个 token → 引入 jieba 预分词，加 fts_text 列、FTS 改索引该列 + 存量迁移回填，查询侧同分词器构造 MATCH。
结果：关键词路召回 0→20。
③ 子块切分死循环 · 后端整体卡死
问题：点讲义索引后，后端不报错、直接整体卡死冻住。
定位/解决：定位到 child_chunker._build_windows 遇「单句长度落在 (max−overlap, max]」反复重试同一句、阻塞整个 asyncio 事件循环 → 改逐句消费 + 长句硬切，补 _test_chunk_windows 回归。
结果：不再死循环，回归用例锁死行为防复发。
④ 第三方不确定性：格式漂移 + 空幽灵块
问题：MinerU 官网文档滞后且与实测不符、还会变；跨页表格吐出 html 为空的伪块，污染检索。
定位/解决：以实测反推格式 + 建 19 项语义校验 + 探针日志（有偏差才记、前端告警）；空幽灵块在 normalizer 源头丢弃 + child_chunker 兜底。
结果：格式变化可监控告警；垃圾子块 10→0。
这些都是真机调出来的、不动手遇不到的问题。完整记录见 RELEASE_NOTES / test_v120·v140 回归用例 / 设计原始思考 我的想法.md。
