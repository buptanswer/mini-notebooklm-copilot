## 1. 总体设计快照

### 1.1 新增三大能力

| 能力 | 给谁用 | 简介 |
|------|--------|------|
| **文件夹绑定** | 全局，但课程 KB 必备 | KB 关联到本地一个文件夹路径，同步时自动登记文件；`.txt/.md` 跳过 MinerU |
| **多轮对话基座** | 模块七 / 模块九 | `conversations` + `messages` 两张表，支持 fork 分支、思维链持久化 |
| **场景模块前端** | 课程 KB | 二级侧边栏 + `ReviewPage` + `CourseInfoPage` |

### 1.2 数据流：模块七（课后复习）

```
用户进入课程 KB
  ↓ 选日期（如 260507）
  ↓
后端读取 课堂录音/260507/*.txt （按"第N节"排序）
  ↓
创建新 conversation（scenario=lecture_review, 元数据含课程/日期/节次）
  ↓
循环节次：
   构造 user message = "{首节或后续节模板}\n\n{txt 内容}"
   调用 LLM（流式，可开思维链）→ 持久化为 assistant message
  ↓
前端展示三条 assistant message（即三份"课堂要点"）
  ↓
用户点"保存到本地" → 写入 课堂录音/{date}/{prefix}第N节课堂要点.md
  ↓
用户在同一 conversation 内追问 → 上下文完整保留
  ↓（可选）
用户对某轮回答"fork" → 创建子 conversation 继续问，主线不被污染
```

### 1.3 数据流：模块九（课程管家）

```
用户进入课程 KB → 点"课程管家"
  ↓
首次进入：触发"生成卡片"
  ├─ 后端用 5 个固定查询触发 hybrid_search（在该 KB 内）
  │   - "考核方式 评分标准 成绩比例"
  │   - "作业要求 截止时间 提交方式"
  │   - "考试时间 期中 期末"
  │   - "老师 联系方式 答疑时间 邮箱"
  │   - "重要通知 注意事项"
  ├─ 汇总检索结果 → LLM 一次结构化抽取（JSON 模式）
  └─ 写入 course_info_cards 表
  ↓
前端展示卡片：考核 / 作业与 DL / 老师 / 通知
  ↓（可选）
用户点"针对此课程聊天" → 在卡片基础上多轮问答（复用 conversations）
  ↓
进入此 KB 时若有未来 7 天内的 DL → 顶部黄色 banner 提醒
```

### 1.4 与 v1.1.0 的兼容性

- 现有 `/api/chat` 端点**不动**，作为通用问答保留
- 现有 16 步 pipeline **不动**，但 `_SUPPORTED_EXTENSIONS` 扩展 `.txt`/`.md`，且这两种格式跳过整个 MinerU 流程
- 现有 KB CRUD **不动**，仅追加 `bound_folder_path` 字段（懒迁移）
- 现有 5 张场景模块表里：`review_notes` 表本期**不用**（决定让笔记落到磁盘文件而不是 DB；表保留以便未来扩展）；`course_info_cards` 表用；`exam_*` 表本期不动

## 2. 数据库变更

### 2.1 修改的表

#### `knowledge_bases` 加 1 列

```sql
ALTER TABLE knowledge_bases ADD COLUMN bound_folder_path TEXT DEFAULT '';
-- 也加到主 DDL，幂等
```

`bound_folder_path` = 用户指定的本地文件夹绝对路径，空字符串表示未绑定（兼容旧的"上传式"KB）。

#### `documents` 加 2 列

```sql
ALTER TABLE documents ADD COLUMN bound_file_path TEXT DEFAULT '';
ALTER TABLE documents ADD COLUMN folder_category TEXT DEFAULT '';
```

- `bound_file_path`：在绑定文件夹模式下的真实文件路径（绝对路径）。上传式仍用 `upload_path`
- `folder_category`：约定目录归类，可选值：`recording` / `slides` / `homework` / `notice` / `review_note` / ''（未分类或非绑定模式）

新支持的 `status` 取值（document.status）：
- `text_only`：`.txt` / `.md` 文件，不需解析，直接可用
- 其他保持不变（`uploaded` / `parsing` / `indexed` / `needs_review` / `failed`）

新支持的 `source_format` 取值：`txt`、`md`（除现有 pdf/docx/pptx/jpg/png 外）。

    - 不删除已消失文件的 DB 记录，只把 status 置为 'missing'，让用户手动确认

    - 幂等：同一文件不会被重复登记（通过 kb_id+bound_file_path 唯一约束）

def _categorize(relative_path: str) -> str:
    """根据相对路径第一段映射 folder_category"""

def _is_text_format(ext: str) -> bool:
    """判定 .txt/.md（含变体如 .TXT）"""

实现要点：
- 用 `Path(folder).rglob('*')` 遍历
- 跳过隐藏文件（`.git`、`.DS_Store`、`Thumbs.db`、`~$*`）
- 跳过 0 字节文件
- 文件标识用 `(kb_id, bound_file_path)`；不依赖文件名稳定性
- 已消失文件标记 `status='missing'`（新增状态值，前端显示灰色）

#### 3.2.2 加载器（`__init__.py`）

```python
"""
提示词加载器：从 backend/app/prompts/ 目录读取 .md 文件作为提示词。
约定：每个 .md 文件名（不含扩展名）= prompt name。
支持简单变量替换 {var}（Python str.format）。
启动时一次性加载所有 .md 到内存。
"""
from pathlib import Path
from typing import Any

_PROMPT_DIR = Path(__file__).parent
_cache: dict[str, str] = {}

def _load_all() -> None:
    for p in _PROMPT_DIR.glob("*.md"):
        _cache[p.stem] = p.read_text(encoding="utf-8")

def load_prompt(name: str, **vars: Any) -> str:
    if not _cache:
        _load_all()
    if name not in _cache:
        raise KeyError(f"prompt '{name}' 不存在于 {_PROMPT_DIR}")
    template = _cache[name]
    return template.format(**vars) if vars else template

def list_prompts() -> dict[str, str]:
    """返回 {name: full_text}，供 Settings 页展示。"""
    if not _cache:
        _load_all()
    return dict(_cache)

def reload_prompts() -> None:
    """显式重载（用户在 Settings 页改文件后调用）。"""
    _cache.clear()
    _load_all()
```

#### 3.3.3 流式生成核心逻辑（伪代码）

```python
async def stream_completion(conversation_id, user_content, ...):
    # 1. 先写入 user message（落库后才开始生成）
    conv = await get_conversation(conversation_id)
    user_msg_id = await append_message(
        conversation_id, "user", user_content, metadata=user_metadata or {}
    )
    yield sse({"type": "user_message_appended", "message_id": user_msg_id})

    # 2. 拉历史消息组装 OpenAI messages
    msgs = await list_messages(conversation_id)
    openai_msgs = [{"role": m["role"], "content": m["content"]} for m in msgs]

    # 3. 如有 RAG 注入，把 user_content 改写
    if inject_context_chunks:
        last = openai_msgs[-1]
        last["content"] = build_rag_user_content(last["content"], inject_context_chunks)

    # 4. 调 LLM 流式接口
    accumulated_content, accumulated_thinking = [], []
    async for evt in _call_llm_stream(openai_msgs, enable_thinking=conv["enable_thinking"]):
        if evt["type"] == "thinking":
            accumulated_thinking.append(evt["content"])
            yield sse(evt)
        elif evt["type"] == "delta":
            accumulated_content.append(evt["content"])
            yield sse(evt)

    # 5. 落库 assistant message
    assistant_msg_id = await append_message(
        conversation_id, "assistant",
        content="".join(accumulated_content),
        thinking="".join(accumulated_thinking),
        citations=inject_context_chunks or [],
    )
    yield sse({"type": "assistant_message_appended", "message_id": assistant_msg_id})
    yield sse({"type": "end"})
```

`_call_llm_stream` 直接复用现有 `qa_service` 内部的 httpx 调用逻辑。最干净的做法：把 `qa_service.stream_answer` 内部的"调 LLM"部分抽到一个独立函数 `qa_service._stream_llm(messages, enable_thinking)`，conversation_service 与原 `stream_answer` 共用。

#### 3.5.4 模块七必备的"加分功能"

接手者实现时这些功能不要漏，否则用户会觉得"不如编辑器打开"：

1. **多轮追问**：前端有完整聊天 UI（基于 messages），用户可在生成后继续问
2. **会话 fork**：每条 assistant 消息下方"从此分叉新对话"按钮
3. **思维链开关**：会话顶部 toggle，立即影响下一轮（不影响已生成内容）
4. **历史会话列表**：左侧栏列出本 KB 内所有 lecture_review conversations（按日期分组）
5. **导出**：把当前会话所有 assistant 内容拼一个完整 markdown，浏览器打印 → PDF
6. **关键概念抽取**（轻量加分）：在生成完三节后，自动追加一轮"请列出今天这三节课的核心知识点和它们之间的逻辑关系"
7. **自测题**（轻量加分）：消息下方"基于这节生成5道测试题"按钮，调一次单独的提示词
8. **存盘状态徽标**：每节标题旁标"已存盘"/"未存盘"
9. **章节内 TOC**：长讲义自动渲染目录跳转（用 react-markdown 的 rehype-slug + rehype-autolink-headings）

8. 关 thinking 重新追问 → 看不到 thinking 流

### 7.3 边界与容错

- KB 没绑定文件夹 → 同步端点返回 400 / `{detail: "未绑定"}`
- bound 路径不存在或无权限 → 报错信息友好
- .txt 文件含 BOM / GBK 编码 → 用 chardet 兜底；至少 UTF-8 with BOM 要处理
- 一节 .txt 内容超长（> 100KB） → 单次 LLM 调用可能超 token，超过 50KB 时分两条 user message 喂入
- 同名 conversation fork 多次 → 各 ID 独立，UI 应能区分

## 8. 风险与降级

| 风险 | 影响 | 降级 |
|------|------|------|
| LLM 返回 JSON 不合法（课程管家） | 卡片生成失败 | `course_info_service`：JSON parse 失败时重试 1 次，提示更严格；二次失败把 raw response 写入 important_notes 让用户手动整理 |
| .txt 编码不可识别 | 模块七生成乱码 | 用 `chardet` 探测，失败时回退 `errors="replace"`，前端提示"原文可能有乱码" |
| 单节 .txt 超长（> 100KB） | LLM 截断 | 自动按段落切分喂入（每条 ≤ 50KB） |
| 文件夹同步时间长（数千文件） | 接口超时 | 走 BackgroundTasks，sync API 立即返回 task_id，前端轮询 |
| deadline 日期解析失败 | days_left 为 null | UI 不计入 banner，只在卡片中文字展示，标"未能解析日期" |
| Qwen API 不支持 `response_format=json_object` | 课程管家结构化抽取失败 | 提示词强调 JSON 输出 + 后端用 regex 剥离 ```json 标签 |
| 课程 KB 的 .pdf 太多但未解析 | 课程管家检索为空 | 生成卡片前检查是否有任何 indexed 文档，无则提示"先解析至少一个通知文件" |
